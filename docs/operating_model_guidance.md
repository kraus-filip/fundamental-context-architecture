# FCA Operating Model Guidance

Status: supporting guidance for FCA `1.0`
Authority: explanatory guidance; the kernel remains in `blueprint.md`

## Purpose

This document explains how FCA can shape day-to-day operating practices after the minimum kernel is accepted. It focuses on how governed work starts, repeats, varies, and produces reusable knowledge.

The operating model should keep FCA practical. It should help teams reuse governed context and improve it through real work, without turning every task into a manual compliance ritual.

## Adoption Paths

FCA can begin from real work, from the operating model, or from both at once. The starting point changes, but the minimum kernel does not. Each path establishes who holds source authority and how context changes state. It makes boundaries and policy operational. It also defines how context is promoted for reuse and how evidence preserves accountability.

Bottom-up adoption starts from real work. A team begins with a concrete AI-enabled workflow or decision problem. The FCA task is to keep that improvement from becoming an isolated context island. Its inputs remain connected to authority, and useful results follow a governed promotion path so later work can reuse them.

Top-down adoption starts from the operating model and governance surface. The organization establishes how authority is assigned and how governed context moves through its lifecycle. It turns boundary and policy requirements into operational decisions. It also assigns control-plane ownership and defines the evidence that governed work leaves behind before AI-enabled execution expands. The FCA task is to make that foundation usable in real work rather than leaving it as abstract policy.

Hybrid adoption starts with a concrete use case while the minimum governance needed for reuse is established alongside it. This is often the practical early route because it demonstrates value while installing a reusable foundation. The work remains connected to governed sources, its decisions and outputs receive explicit lifecycle status and reviewable evidence, and useful results can be promoted for later work.

No adoption path is automatically superior. The choice reflects how quickly the organization needs to act and how consequential the work is. It also reflects how much governance already exists and how costly it would be to repair context created without authority, lifecycle, or evidence.

## Minimum Responsibility Model

FCA assigns responsibilities before it assigns job titles. One person or team can hold several responsibilities in a small implementation. A larger organization can distribute them through its existing ownership and decision structures. In either case, every responsibility remains explicit enough for governed work to be reviewed.

### Source Owner

A source owner is accountable for the authoritative record and the system in which it is maintained. This owner establishes where source truth resides and who can change it. The same responsibility governs correction and supersession.

### Context Owner

A context owner is accountable for a family of governed context objects and the lifecycle model that applies to it. This owner keeps its vocabulary and reuse rules coherent after context is promoted from local work. Any resulting knowledge product remains governed through the same responsibility. New use cases therefore stay connected to established authority and boundaries. Their lifecycle, evidence, and reuse treatment also remain coherent.

### Policy Or Approval Owner

A policy or approval owner decides whether context may be seen and whether it may support a proposed use or action. This includes decisions about transformation and promotion. It also covers boundary exposure and AI-assisted action. This responsibility remains distinguishable from technical access administration.

### Execution Owner

An execution owner is accountable for the operational surface that uses governed context. That surface can be a workflow, assistant, automation, agent, or another work system. The owner ensures that runtime behavior respects the approved source authority and policy. Lifecycle and evidence conditions continue to apply during execution.

### Evidence And Reviewability Owner

An evidence and reviewability owner defines the trace needed to reconstruct governed decisions and actions. The same responsibility covers exceptions and promotions. It establishes the evidence expectations and review criteria for the scope. It also ensures that retention is handed to the appropriate function and that the resulting evidence is proportionate to risk.

The organization can place this responsibility with an assurance, records, policy, or execution function. Its placement may vary, but accountability remains explicit so that missing or weak evidence can be challenged.

## Minimal Viable FCA Adoption

A minimal first FCA adoption should start with one consequential workflow, use case, decision path, or recurring operational problem. The goal is not to design the whole enterprise at once. The goal is to prove that one useful piece of AI-first or AI-driven work can become governed, reusable, and reviewable instead of remaining an isolated local success.

A first adoption establishes one bounded governed cycle. It identifies the source authority for the selected work and gives the relevant context objects an explicit lifecycle. The scope defines which uses are permitted. It identifies where approval or exception decisions occur and what evidence execution must return. It also defines how useful outcomes are assessed for promotion into reusable governed context.

The selected scope is ready for FCA assessment when its governed cycle can be demonstrated. The trace begins with source authority and explains why the use was permitted. It then records the accountable action and any resulting change. The retained evidence must also show whether the outcome can be reused.

This checkpoint does not create a reduced form of FCA. Conformance remains determined by the Minimum FCA Kernel. Technical sophistication cannot substitute for the governed cycle.

## Start Governed Work With A Context Check

Governed work starts by checking whether relevant context already exists. This happens before an answer or decision is invented. The same principle applies when creating a process or artifact.

The check first locates authoritative sources and prior decisions. It identifies known constraints and existing exceptions. A reusable playbook or template may already support the work. Related domain and boundary context determine whether that material applies.

The check remains lightweight and useful. It prevents reinvention and establishes whether work can proceed under existing governed context. When relevant context, policy, or a boundary is materially insufficient, the work raises a governed challenge rather than silently filling the gap or departing from authority. Work continues only within permitted discretion or through the decision and approval path assigned to the scope.

If no useful source exists, that absence becomes evidence for governance. It can reveal that guidance is missing, that a source has no clear owner, or that an existing source is obsolete. It can also expose an unresolved boundary. Where the work introduces genuinely new context, the absence supports proposing a new governed context object.

## Govern Business Processes And Recurring Workflows

Business processes and recurring workflows define how repeated work is carried out. When one materially shapes governed decisions or actions, its reusable definition forms part of the governed contextual foundation. That definition remains distinct from any one execution instance.

The reusable definition has an accountable owner and a declared purpose. Its scope and lifecycle state determine where it applies and whether it remains current.

It defines what evidence each execution returns and which variations are permitted. It also determines how useful improvements can be promoted. Templates and automation implement that governed design rather than becoming its authority.

An access review repeats on a schedule. Customer onboarding repeats for each customer. Release and procurement approvals repeat whenever governed work reaches the corresponding decision point. Incident reviews follow the same principle. Each run produces its own evidence, but every run relies on a reusable process or workflow definition.

Not every repeated habit qualifies. Governance is warranted when variation could change authority or permitted access. It is also warranted when weak evidence, boundary crossing, or reuse would create material consequences. AI-assisted execution raises the same requirement when the recurring workflow shapes what the system may do.

## Govern Process Variants Explicitly

Processes vary when their operating context differs. A domain or product can require one form of work, while a client or jurisdiction requires another. Risk classification and local operating responsibility can also justify divergence. The difference is represented as an explicit variant rather than an informal copy.

Every variant remains connected to its parent process and accountable owner. Its declared scope shows where it applies. Its rationale states why the divergence is permitted. Review and supersession rules establish when the variant must be reconsidered and which version remains current.

Explicit variants prevent uncontrolled fragmentation. A local exception cannot be mistaken for the organization-wide process. The parent process is not imposed where a governed variant applies.

The objective is governed variation rather than uniformity. Each difference remains scoped and reviewable, while useful variants can be reused where appropriate.

## Promote Reusable Knowledge From Real Work

Real work is where reusable knowledge is tested and discovered. A repeated question can reveal that an authoritative source is unclear. A task may produce a template that later work can reuse. A workaround can expose a gap in the current process. When different teams repeatedly rediscover the same decision, useful context has not yet reached them in a governed reusable form.

Useful working context enters promotion rather than becoming shared guidance automatically. Promotion establishes its source basis and accountable owner. It declares where the context applies and how its lifecycle is governed. Boundary rules control whether protected material can be reused, while evidence preserves the promotion decision.

Contribution is valued by future usefulness rather than volume. Producing more notes does not strengthen the contextual foundation by itself. A valuable contribution improves later work or reduces reinvention. It can clarify authority and make AI-assisted execution safer.

## Keep Operating Guidance Proportional

Operating guidance scales with consequence and expected reuse. Work that changes access or crosses a protected boundary requires explicit approval and evidence. The same applies when work creates a consequential external result, implements a regulated decision, or changes production operation. A low-risk internal draft uses lighter controls while retaining source reference and lifecycle clarity.

Proportionality keeps FCA useful rather than obstructive. The operating model makes governed work easier to repeat, review, and improve while concentrating heavier control where the consequences justify it.
